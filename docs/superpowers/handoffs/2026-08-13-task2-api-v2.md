## Migration Strategy

### Parallel Run Model
- v1 and v2 endpoints coexist indefinitely
- No breaking changes to v1
- Clients migrate endpoint-by-endpoint at their own pace

### Backward Compatibility
- v2 responses are **superset** of v1
- All v1 fields preserved in v2 models
- New fields are optional with sensible defaults

### Client Migration Path
```typescript
// Before (v1)
const watchlist = await get<WatchlistItem[]>("/api/watchlist");

// After (v2) — same data + enriched metadata
const watchlist = await getWatchlistV2();
// New fields: instrument_type, bid, ask, oi, is_tradable
```

## Technical Details

### V2 Model Enhancements

**WatchlistItemV2** (extends WatchlistItem):
```typescript
{
  // All v1 fields...
  instrument_type: string | null;  // INDEX / EQUITY / FUTURES / OPTION
  bid: number | null;
  ask: number | null;
  oi: number | null;
  is_tradable: boolean;
}
```

**OptionsChainResponseV2** (extends OptionsChainResponse):
```typescript
{
  // All v1 fields...
  spot: number | null;           // Underlying spot price
  max_pain: number | null;       // Max pain strike
  pcr: number | null;            // Put-call ratio
  iv_rank_percent: number | null; // IV rank percentile
  contracts: OptionsChainItemV2[]; // With spot_distance_pct
}
```

### Implementation Notes

1. **Reuse v1 logic**: v2 endpoints delegate to v1 hydration/fetch functions
2. **Aggregate analytics**: Options chain v2 includes max_pain, pcr, iv_rank in single response
3. **Spot distance**: Each contract includes % distance from spot price
4. **Type safety**: `option_type` constrained to `Literal["CE", "PE"]` in v2
